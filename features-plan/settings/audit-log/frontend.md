# System Audit Log & Activity Trail

## 1. Module
Settings

## 2. Name
System Audit Log & Activity Trail

## 3. Description
The System Audit Log & Activity Trail is the immutable, centralized tracking engine for the Business Execution System (BES). It acts as the ultimate source of truth for compliance, security monitoring, and process troubleshooting. Unlike application-specific logs, this feature records the "5 Ws" (Who, What, When, Where, and Why) of every critical transaction and configuration change across all modules (Finance, Sales, HR, etc.). It serves as the data foundation for the `Timeline` Process Transparency components embedded throughout the UI, allowing administrators to trace the complete lineage of any record.

## 4. Depends on
- **User Management & RBAC (Settings):** To identify the `user_id` performing the action and evaluate permissions for viewing logs.
- **Company / Entity Setup (Settings):** To ensure audit logs are strictly partitioned by `subsidiary_id`.
- **Core Integration:** Core provides the unified `BESBase` foundation. The `core.audit_logs` table sits at the lowest level of the architecture, acting as a sink for events generated by all other schemas (`sales`, `finance`, `hr`, etc.).
- **Other Dependencies:**
  - `@bes/shared-ui` for the data-dense Audit Log Data Grid and the vertical `Timeline` component.

## 5. Feature name, details - the UI as information
**Feature Name:** Centralized Audit Viewer
**Details & UI Information:**
- **Resource List (Audit Grid):** A highly performant, read-only data grid designed to handle millions of rows. Columns: `Timestamp`, `User` (Name/Email), `Module` (e.g., Finance, HR), `Action` (CREATE, UPDATE, DELETE, APPROVE, LOGIN), `Entity/Record ID` (Hyperlink to the actual record), and `IP Address`.
- **Advanced Filtering Drawer:** A slide-out panel allowing security officers to filter the massive dataset by `Date Range`, `Specific User`, `Module`, `Action Type`, or search for a specific `Record ID`.
- **Diff Viewer (Modal):** Clicking on an "UPDATE" action opens a modal showing a visual, side-by-side JSON diff of `previous_state` vs `new_state`.
- **Empty States:** Given the nature of the system, this will never be empty after the first user logs in. If filtered to zero results: "No audit events match your strict filter criteria."
- **Loading States:** Server-side pagination indicators and skeleton loaders during complex filtered queries.

**User Journey & UX Flow:**
1. Security Officer navigates to **Settings > System Audit Log**.
2. User applies a filter: `Module = HR`, `Action = UPDATE`, `Date = Last 7 Days`.
3. System returns a paginated list of all HR modifications.
4. User clicks on a specific row regarding an "Employee Base Salary Update".
5. A modal opens, displaying the exact timestamp, the IP address of the HR Manager, and a side-by-side JSON comparison showing the salary changing from `$100,000.0000` to `$120,000.0000`.
6. Alternatively, standard users interact with this module invisibly every day when they look at the **Timeline** tab on any specific record (e.g., viewing a Sales Order drawer automatically queries the Audit Log filtered down to that specific `record_id`).

## 7. Required APIs
- **GET `/api/v1/core/audit-logs`**: Fetch paginated, server-side filtered audit records. Requires high-level security permissions.
- **GET `/api/v1/core/audit-logs/record/{table}/{record_id}`**: Optimized endpoint used by the frontend `Timeline` components to fetch the linear history of a *specific* record (e.g., all events for a single Purchase Order).
- **POST `/api/v1/core/audit-logs/export`**: Triggers a background job to export filtered audit logs as a secure CSV/PDF for external compliance auditors.

## 8. Database Tables & Architecture
### Schema: Core Module
#### Table: `core.audit_logs`
- **Inherits**: Conceptually similar to `BESBase`, but heavily optimized for append-only, high-volume inserts. Often partitioned by `timestamp` (e.g., monthly partitions).
- `id`: UUID (Primary Key)
- `subsidiary_id`: UUID (NOT NULL) - For strict scoping.
- `user_id`: UUID (FK to `core.users`)
- `timestamp`: Timestamp (NOT NULL, Indexed)
- `module_name`: String (Indexed)
- `action_type`: String (Indexed)
- `record_table`: String (Indexed alongside `record_id`)
- `record_id`: UUID (Indexed alongside `record_table`)
- `previous_state`: JSONB
- `new_state`: JSONB
- `ip_address`: String
- `user_agent`: String

## 9. Events & Real-Time Updates (Pub/Sub)
- **Emits:**
  - `settings.audit.anomaly_detected`: (Future AI Phase) Triggered if the volume of `DELETE` or `EXPORT` actions by a single user breaches predefined thresholds.
- **Listens To:**
  - **ALL MODULE EVENTS:** The Audit Log is the ultimate subscriber. It intercepts backend ORM lifecycle hooks (Before/After Save/Update/Delete) across the entire codebase to automatically construct and persist the audit payloads synchronously or via high-throughput queues.

## 10. Business Rules & Validations
- **Absolute Immutability:** Audit records CANNOT be updated or deleted by ANY user, including the Super Admin. The `UPDATE` and `DELETE` SQL commands are revoked at the database user level for the `core.audit_logs` table.
- **Data Pruning / Archival:** Records older than statutory requirements (e.g., 7 years) are not deleted, but moved to cold storage (e.g., AWS S3 Glacier) via automated background jobs.
- **Performance Protection:** Queries against the central audit log must enforce a mandatory `Date Range` limit (e.g., maximum 30 days per query) to prevent database lockups, unless using the asynchronous Export API.

## 11. Security, Audit, and RBAC
- **Roles:**
  - `System Auditor / Security Officer`: Has global read-only access to the central Audit Viewer and Export functionalities.
  - `Entity Admin`: Can view the central Audit Viewer, but the backend forces a `subsidiary_id` filter matching their context.
  - `Standard User`: Cannot access the central Audit Viewer, but CAN view the filtered `Timeline` tab for specific records they have permission to access (e.g., a Sales Rep viewing the timeline of their own Sales Order).
- **Read-Only Licensing:** Since the Audit Log is inherently read-only, it remains fully functional and accessible for auditing purposes regardless of standard transactional licensing blocks.

## 12. Process Transparency & Workflow Pipeline
- **Process UI Integration:**
  - **Micro View (`Timeline`):** This entire module serves as the backend engine that powers the `Timeline` view found in the "History/Activity" tab of *every* other Drawer in the system (Sales Orders, Invoices, Employee Profiles).
- **Traceability:** It provides the raw, unalterable data proving the lineage of any transaction.
- **Navigation:** Main Sidebar > Settings > Audit & Compliance.

## 13. Technical Implementation Roadmap
- **Phase 1: Backend Foundation:** Create the `core.audit_logs` table with appropriate composite indexes (`subsidiary_id`, `record_table`, `record_id`, `timestamp`). Configure database-level append-only constraints.
- **Phase 2: Core Logic & APIs:** Implement the global ORM interceptor (e.g., Prisma Middleware or TypeORM Subscriber) to automatically catch state changes, compute JSON diffs, and fire async queue workers to write to the audit table without blocking the main transactional request.
- **Phase 3: Frontend Infrastructure:** Register the Audit Viewer component in the `@bes/settings` library.
- **Phase 4: UI Development:** Build the highly optimized data grid and the JSON Diff Modal. Hook the existing shared `Timeline` component to consume the `/record/{table}/{id}` API endpoint.
- **Phase 5: Performance Tuning:** Implement table partitioning strategies for high-volume deployments.

## 14. Verification & QA Strategy
- **Immutability Check:** Attempt to execute a `PUT` or `DELETE` API request against an existing `audit_log` ID. Verify the API returns a `405 Method Not Allowed` or `403 Forbidden`. Attempt a direct SQL update; verify the DB user rejects it.
- **Scoping Enforcement Check:** Log in as an Admin of Subsidiary A. Attempt to manually query the audit log endpoint with a `record_id` belonging to Subsidiary B. Verify the response is empty or `403 Forbidden`.
- **Functional Scenarios:**
  1. Create a Draft Sales Order. Update its Total Amount. Delete it.
  2. Navigate to the Central Audit Log and verify that exactly three entries (CREATE, UPDATE, DELETE) were generated, containing the correct `previous_state` and `new_state` payloads.
  3. Verify the JSON Diff viewer highlights the exact changed fields.
- **Integration Test:** Verify that the frontend `Timeline` component inside a specific module's drawer correctly renders the localized, human-readable history utilizing data fetched from the Audit Log.
